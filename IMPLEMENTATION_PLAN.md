The backend pipeline already works correctly — `python3 run_bridge.py scan <path>` produces real findings with Mosca scores and fix suggestions. **No ML model is needed or appropriate here.** The entire detection, scoring, and fix-generation system is deterministic rule-based code, which is the right call for a compliance/audit tool (explainability > black-box accuracy).

The problems are:

1. **`python` command not found** — `backendRunner.js` calls `python`, the system only has `python3`
2. **`GitPython` not installed** — GitHub URL scanning crashes silently
3. **`python` command** — `backendRunner.js` calls `python`, system only has `python3`
4. **No `requirements.txt`** — new team members / CI have no reproducible install
5. **Signature coverage is thin** — only 8 patterns across 2 languages; misses Go, C/C++, JavaScript, TypeScript, Kotlin, Ruby, PHP, Rust, config files (`.env`, YAML, TOML), and Docker
6. **File size cap too aggressive for "big repos"** — 2000 files / 200MB blocks any real enterprise repo

8. **`reports/route.js` falls back to a hardcoded `scan` on empty path** — calls backend with no target, crashes silently, serves hardcoded demo data
9. **`cbom/route.js` not read yet** — may have similar issues
10. **Fix suggestions are string-replace only** — correct for simple cases but needs expansion for more language idioms

## Answer: Do You Need an ML Model?

**No. Absolutely not.** Here is why:

- Cryptographic API usage follows **deterministic, well-known patterns** — `RSA.generate(1024)`, `MessageDigest.getInstance("MD5")`. These are library calls with documented signatures. A regex/AST scanner against a signature list catches them with near-zero false positives.
- The fixes are **also deterministic** — replace MD5 with SHA-256, replace RSA with ML-KEM-768. NIST has published the exact replacement for every deprecated algorithm. This is a lookup table, not a prediction.
- Mosca's risk scoring is **a formula, not a model** — `risk_gap = (X + Y) - Z`. The inputs are heuristics from file paths and known constants. It is transparent, auditable, and defensible in a Q&A.
- **An ML model would actively hurt you** — judges will ask "how does it decide?" A rule-based system has a one-sentence answer. A model does not.

The `suggested_fix` field is generated by the `fix_templates.py` file — template-based string substitution. This is correct and sufficient. For fixes that don't have a template, the fallback is `manual_review` with a comment pointing at the NIST standard. That is honest and appropriate.

## Big Repo Support

### Current limits in `config.py`:
```python
MAX_REPO_FILE_COUNT = 2000   # too small — react/angular repos routinely exceed this
MAX_REPO_SIZE_MB = 200       # reasonable but blocks some repos
```

### Problems:
1. **`node_modules/` is already excluded from scanning** but still counted in the file limit — a repo with `node_modules/` will hit 2000 files even if only 50 are actual source files
2. **The limit applies before scanning** — it rejects repos before checking if the code files are even within limit

### Fix strategy:
- Count only **scannable files** (`.py`, `.java`, `.js`, `.ts`, `.go`, `.c`, `.cpp`, `.h`, `.kt`, `.rb`, `.php`, `.rs`, `.env`, `.yml`, `.yaml`, `.toml`, `.properties`, `.crt`, `.pem`, `.csr`) toward the file count cap
- Raise cap to `MAX_REPO_FILE_COUNT = 10000` (scannable files only)
- Keep size cap at 200MB but apply it to scannable content only, not `.git/` and `node_modules/`
- Add streaming output for large repos: write findings to stdout incrementally as each file is processed, rather than accumulating everything in memory first

## Fix Generation — How It Works (No Model Needed)

The current system already generates real, correct fixes. Here is the full picture:

### Tier 1 — Template-based exact fix (already implemented)
For the top ~10 most common patterns, `fix_templates.py` has a regex that matches the original line and a lambda that produces the fixed line. This covers MD5→SHA-256, SHA1→SHA-256, DES→AES, RSA→ML-KEM comment, TLS1.0→TLS1.3, etc.

**Output example:**
```python
# Before (original_code)
return hashlib.md5(data.encode()).hexdigest()

# After (suggested_fix)
return hashlib.sha256(data.encode()).hexdigest()  # Upgraded to SHA-256 (NIST FIPS 180-4)
```

### Tier 2 — Algorithm-family fallback (already implemented)
If no template matches, `fix_templates.py` does a string-replace on the algorithm name in the original line with the PQC replacement name, plus a NIST citation comment.

### Tier 3 — Manual review flag (already implemented)
If no template and no family fallback, `fix_confidence = "manual_review"` with a comment citing the NIST standard. This is honest and correct — better than a hallucinated fix.

### What to expand (no model, just more templates):
- Add JS/TS fix templates for Node.js `crypto` module
- Add Go fix templates for `crypto/md5`, `crypto/rsa`, etc.
- Add C/OpenSSL fix templates (just show the EVP API equivalent)
